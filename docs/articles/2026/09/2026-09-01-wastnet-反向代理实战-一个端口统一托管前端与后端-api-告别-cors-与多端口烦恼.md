# 🚀 wastnet 反向代理实战：一个端口统一托管前端与后端 API，告别 CORS 与多端口烦恼

## 📝 一句话总结

wastnet 作为一款零依赖、自研 NIO 的 Java Web 服务器，通过内置反向代理能力，让开发者用一个端口同时托管前端静态资源与后端 API，简化部署架构并提升性能。

---

## 📌 核心内容

- 🔹 **零依赖自研内核**：wastnet 完全基于 JDK 原生 NIO 构建，不依赖 Netty、Tomcat 等第三方网络库，核心协议栈（HTTP/2、HPACK、Huffman、ALPN）均为自研实现，展现极致的技术掌控力。
- 🔹 **反向代理一体化**：通过 wastnet 的反向代理模块，可将前端静态资源（如 Vue/React 构建产物）与后端 API（如 Spring Boot 服务）统一监听在同一个端口，由 wastnet 根据路径规则智能转发，有效解决开发与生产环境中的跨域（CORS）问题。
- 🔹 **HTTP/2 原生支持**：支持 h2 / h2c 协议，从 HPACK 压缩到 ALPN 协商均自主实现，意味着更低的延迟和更高的吞吐，尤其适合现代 Web 应用。
- 🔹 **高性能基准**：在基准测试中，wastnet 展现出优于传统 Servlet 容器的吞吐能力，适合对性能有苛刻要求的场景。
- 🔹 **简化部署架构**：原本需要 Nginx + Tomcat 或多个端口配合的部署模式，现在可被 wastnet 单节点替代，降低运维复杂度。

## 🎯 为什么值得关注

- 🎯 **解决真实痛点**：前后端分离开发中，跨域问题与多端口配置一直是 Java 开发者的日常烦恼。wastnet 的一端口方案直击痛点，让本地开发和生产部署都变得清爽。
- 🧠 **深入理解网络层**：wastnet 自研 NIO 和 HTTP/2 协议栈，阅读其源码或原理，能帮助 Java 开发者加深对网络编程、Reactor 模型和 HTTP 协议的理解，这是使用 Tomcat 等黑盒容器难以获得的收获。
- ⚡ **性能敏感型应用福音**：如果项目对吞吐量和延迟有较高要求，且希望避免引入重量级网关（如 Nginx），wastnet 提供了一个轻量、可控的替代方案。
- 🔧 **技术视野拓展**：作为 Java 生态中的新兴项目，wastnet 展示了 Java 在底层网络领域的潜力，打破“Java 网络编程必须依赖 Netty”的刻板印象。

## ✨ 技术亮点

- **新增功能**：内置反向代理能力，支持基于路径的请求转发，可同时托管静态资源与 REST API，无需额外配置 CORS。
- **架构变化**：采用 Reactor 多路复用模型，单线程或少量线程即可处理海量并发连接，架构上比传统阻塞 I/O 模型更具扩展性。
- **性能优化**：自研 HTTP/2 协议栈，包括 HPACK 头部压缩和 Huffman 编码，有效减少网络传输数据量；NIO 事件驱动模型降低线程上下文切换开销。
- **最佳实践**：推荐将 wastnet 作为边缘服务器，统一暴露 80/443 端口，内部通过反向代理路由到不同微服务，实现类似 API 网关的轻量功能。
- **API 变化**：面向开发者提供简洁的 API 来配置静态资源映射和代理规则，与 Spring Boot 的 `application.yml` 风格类似，学习曲线平缓。
- **兼容性**：基于 JDK 标准 NIO，天然兼容 Java 8+（需确认），且不依赖第三方库，可无缝嵌入现有 Java 项目或独立运行。

## 💭 我的思考

作为一名 Java 后端工程师，看到 wastnet 这类项目时，我的第一反应是“又一个轮子”，但深入了解后，我发现它确实有独特的价值。

**是否值得学习？** 非常值得。wastnet 的核心价值不在于“又写了一个 Web 服务器”，而在于它从零实现了 HTTP/2 协议栈和 NIO 模型。对于 Java 开发者而言，阅读这类源码是提升网络编程内功的绝佳途径。即便是使用 Spring Boot 的开发者，也能从中理解 Reactor 模型如何工作，以及为什么 Netty 能成为高性能的代名词。

**适用场景？** 最适合中小型项目或微服务架构中的边缘节点。例如，一个内部系统需要同时提供前端页面和 API，但又不想引入 Nginx 或额外维护多个端口，wastnet 可以作为独立的 Java 进程运行，配置简单，部署方便。此外，在嵌入式设备或资源受限的环境中，零依赖的特性也很有吸引力。

**未来趋势？** 随着 HTTP/2 和即将普及的 HTTP/3 的发展，Java 生态中自研协议栈的项目会越来越多。wastnet 目前是一个小众项目，但它的方向符合“轻量、高性能、云原生友好”的趋势。如果它能持续维护并完善生态，未来有望成为 Netty 的补充选项。

**是否值得生产环境使用？** 目前持谨慎态度。虽然基准测试数据亮眼，但生产环境需要长期稳定性、丰富的监控工具和社区支持。如果 wastnet 能提供类似 Spring Boot Actuator 的监控端点，并解决内存泄漏等边缘问题，我会考虑在非核心服务中试用。

**与 Spring AI 是否有关？** 目前没有直接关系。但若 wastnet 能成为 AI 应用的后端服务器，它可能为 Spring AI 项目提供高性能的 HTTP 通道，特别是在需要流式响应（SSE）的场景下，其 NIO 模型能更好地支持长连接。

**是否可以结合 RAG？** 可以。RAG（检索增强生成）应用通常需要同时服务静态前端（聊天界面）和动态 API（检索与生成）。wastnet 的一端口反向代理能力，可以简化 RAG 应用的部署，避免为静态资源和模型推理 API 分别配置端口和 CORS。

**是否值得后续写专题？** 绝对值得。我可以围绕 wastnet 写一系列文章，包括源码解析、与 Spring Boot 集成、性能压测、以及如何用它搭建一个完整的 RAG 应用。这不仅有助于技术沉淀，也能帮助更多 Java 开发者认识这一新兴工具。

**总结**：wastnet 是一个技术味十足的项目，虽然还不成熟，但它所代表的“自研、轻量、高性能”理念，正是 Java 生态未来演进的方向之一。我会持续关注，并计划在合适的项目中试点。
