# Spring AI 2.1 重构消息模型：让推理模型的「思考」在往返中不丢失

## 📝 一句话总结

Spring AI 2.1 将 Message 内容重构为有序的 Message Parts 列表，从根本上解决了推理模型思考块、签名、加密推理项在多轮请求中丢失或错序的问题。

---

## 📌 核心内容

- 🧠 **推理模型的新契约**：Claude 会对 thinking block 签名，Gemini 在 function call 上附加 thought signature，OpenAI Responses API 返回加密的 reasoning item。这些数据必须在下一轮请求中原样回传。
- ⚠️ **旧模型的缺陷**：Spring AI 之前的 Message 只是「一段文本 + 工具调用/媒体等旁路列表」，没有位置概念，无法承载推理块，更无法保证顺序。丢弃、重排或编辑这些块，轻则 HTTP 400，重则模型静默丢失上下文重新开始推理。
- 🔄 **数据模型级重构**：Spring AI 2.1 中每条 Message 的内容变为**有序的 Message Part 列表**，Part 是响应的一个片段（文本段、推理块、工具调用等）。
- 🏷️ **跨厂商术语统一**：Anthropic/Bedrock 叫 content blocks，Gemini 叫 parts，OpenAI Responses 叫 items，Mistral 叫 chunks——Spring AI 用统一的 Part 抽象抹平差异。
- 📚 **配套文档齐全**：官方提供 Message Parts Doc、Upgrade Notes、OpenAI Responses Doc、Session Doc，升级路径清晰。
- 🔗 **顺序即语义**：Part 的顺序本身携带信息，回传时不能重排，这是本次重构的关键约束。

## 🎯 为什么值得关注

- 🎯 **踩坑预警**：如果你正在用 Spring AI 接入 Claude 或 Gemini 的推理模型做多轮 Agent，很可能已经遇到「模型莫名失忆」或 400 错误，本文直击根因。
- 🏗️ **架构层面的变化**：这不是加个字段的小改动，而是 Message 数据模型的重构，直接影响你如何构造、持久化、序列化对话历史。
- 🔌 **多模型适配的必修课**：企业级应用往往要同时对接多家 LLM，Part 抽象让「一套代码适配多厂商推理协议」成为可能。
- 📈 **Agent 场景的刚需**：工具调用 + 推理链是 Agent 的核心，Part 模型让推理块与 tool call 能按原始顺序完整往返。
- 🚀 **升级窗口期**：2.1 提供 Upgrade Notes，现在是评估迁移成本的最佳时机。

## ✨ 技术亮点

- ✨ **新增能力**：Message 支持承载 reasoning block、thought signature、encrypted reasoning item 等结构化推理数据，并保证有序回传。
- 🏛️ **架构变化**：从「文本 + 旁路列表」的扁平结构，升级为「有序 Part 列表」的组合结构，Part 成为一等公民，为未来新类型（如音频、引用、缓存标记）预留扩展点。
- 🔤 **API 变化**：构造 Message 的方式改变，需通过 Part 列表组装；旧代码需按 Upgrade Notes 迁移，文本消息可视为单 TextPart 的特例。
- 🧩 **兼容性**：通过统一抽象兼容 Anthropic content blocks、Gemini parts、OpenAI Responses items、Mistral chunks 四套厂商协议，降低多模型切换成本。
- 🛡️ **正确性保障**：顺序敏感设计避免了因重排导致的静默降级（模型丢失推理上下文），把「隐性 bug」变成「显式数据结构」。
- 📐 **最佳实践**：对话历史持久化时应序列化整个 Part 列表而非拼接文本，Session 文档给出了会话管理的参考实现。

## 💭 我的思考

站在 Java 后端工程师的角度，这次改动值得高度关注，甚至可以说是「必须学习」——因为它解决的是一个非常隐蔽、但一旦踩中极难排查的生产问题。

**是否值得学习？** 绝对值得。过去我们用 Spring AI 做多轮对话时，习惯把 assistant 的回复当成一段 String 存进数据库，tool call 单独存一张表。这个心智模型在 GPT-3.5 时代没问题，但推理模型来了之后彻底失效：Claude 的 thinking block 带签名，你把它拼成纯文本再回传，签名就废了；Gemini 的 thought signature 挂在 function call 上，顺序错了模型就重新思考。这类问题不会抛异常，只会让 Agent 的回答质量悄悄下降，线上排查成本极高。Part 模型把这个隐式契约显式化了，是架构上的正确方向。

**适用场景**：凡是涉及 reasoning model 的多轮 Agent、需要 tool calling 的复杂工作流、以及跨厂商 LLM 网关类系统，都是直接受益方。尤其是做 AI Gateway 或统一对话中台的团队，Part 抽象能大幅减少适配层代码。

**是否值得上生产？** 建议先在非核心链路验证。2.1 是数据模型级重构，升级意味着历史消息的存储格式、序列化逻辑、前端渲染都要跟着改。如果你们把对话历史存在 MySQL/Redis 里，需要设计迁移方案——旧数据可降级为单 TextPart 读取，新数据按 Part 列表存储。稳妥路径是：新会话走新模型，旧会话只读兼容，灰度一段时间再全量。

**与 RAG 的结合**：Part 模型对 RAG 其实是利好。检索到的文档片段、引用来源（citation）未来完全可以作为一种 Part 类型承载，和推理块、文本一起有序回传，前端渲染引用标注会更自然。目前虽然还没看到官方 citation part，但抽象已经铺好路。

**未来趋势**：我判断「结构化、有序、可往返的模型输出」会成为 LLM 应用层的事实标准。OpenAI、Anthropic、Google 都在往这个方向收敛，Spring AI 抢先做了统一抽象，这对 Java 生态是加分项。后续很可能出现 Part 级别的流式处理、Part 级别的缓存（prompt caching 按块命中）等能力。

**是否值得写专题？** 非常值得。我计划后续写三篇：一是 Part 模型的数据结构与序列化实战；二是从旧 Message 迁移到 Part 的踩坑记录；三是基于 Part 构建多厂商推理 Agent 的完整示例。这个主题有足够的技术深度和实战价值，值得深挖。
